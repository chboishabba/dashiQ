# Quantum Bridge Interface

This note turns the current Agda quantum split into a concrete implementation
interface for `dashiQ`.

The concrete ZKP-aligned architecture note for this now lives in
`QUANTUM_ZKP_ARCHITECTURE.md`, and the first code skeleton lives in
`quantum_bridge.py`.

The immediate goal is not quantum hardware. The goal is an internal bridge:

1. represent latent quantum-like state in a way that can host DASHI structure
2. separate invertible evolution from non-invertible measurement
3. make observables and coarse statistics explicit
4. identify which existing `dashifine/newtest` modules already realize parts of
   that interface

That gives a clean simulator-facing layer first. Compilation to actual quantum
hardware comes later, if the bridge stabilizes.

## Canonical source split

The current Agda reference spine is:

- `DASHI.Algebra.QuantumInterface`
- `DASHI.Algebra.Quantum.Measurement`
- `DASHI.Algebra.Quantum.Unitary`
- `DASHI.Algebra.Quantum.CCRFromProjection`
- `DASHI.Quantum.Stone`

Read operationally, that spine says:

```text
state
-> invertible evolution
-> measurement / projection
-> observable / entropy-like summary
```

with optional extension seams for:

- CCR / Weyl structure
- continuous-time Stone evolution
- spin / Clifford / signature bridges downstream

## Bridge-first interface

The smallest useful `dashiQ` interface is:

```python
from dataclasses import dataclass
from typing import Protocol, Any

State = Any
Datum = Any

class InvertibleEvolution(Protocol):
    def step(self, state: State) -> State: ...
    def inv(self, state: State) -> State: ...

class Measurement(Protocol):
    def measure(self, state: State) -> Datum: ...
    def project(self, state: State) -> State: ...

class Observable(Protocol):
    def evaluate(self, state: State) -> float | complex | dict[str, float]: ...

@dataclass
class QuantumBridgeSystem:
    state: State
    evolution: InvertibleEvolution
    measurement: Measurement
    observable: Observable
```

This is intentionally minimal.

The key semantic constraints are:

- `step` is intended to be invertible or unitary-like
- `project` is intended to be idempotent and lossy
- `measure` may return a classical datum, not necessarily a new quantum state
- `observable` is not measurement itself; it is a derived quantity on the latent
  state

## Semantics of the four seams

### 1. State

`State` is the latent carrier. In practice this may be:

- a complex statevector
- a density matrix
- a real 2-plane carrying a local complex structure `J`
- a qutrit or 27-state ternary embedding
- a structured lattice state with local wall modes

What matters is that the state is richer than the observed datum.

### 2. Invertible evolution

This is the "unitary-like" seam.

Typical realizations:

- matrix multiplication by a reversible operator
- Hamiltonian or Heisenberg evolution
- lattice propagation using local rotation blocks
- phase rotation generated by a local quarter-turn `J`

If an update rule is not plausibly invertible, it belongs on the measurement or
coarse-graining side, not here.

### 3. Measurement / projection

This is the "collapse" seam.

It has two distinct operations:

- `project(state) -> state_like`: coarse state inside the same carrier family
- `measure(state) -> datum`: classical report or sample

`project` should be treated as idempotent and lossy. If it were invertible, it
would not be acting as measurement in the Agda sense.

### 4. Observable

An observable is any stable scalar, tensor, or report extracted from latent
state without conflating that extraction with measurement itself.

Examples:

- energy or spectral gap
- CHSH `S`
- correlation tensor
- motif distribution
- entropy / MDL proxy / code length

## Optional extension seams

### CCR / Weyl seam

If the bridge grows beyond toy state evolution, the next algebraic seam is:

- translation-like operators
- projection covariance
- Weyl / CCR relations

This belongs after the base interface is stable.

### Stone seam

Continuous-time evolution belongs here:

- generator
- strongly continuous one-parameter group
- state distance or continuity metric

This is the right place to attach wave or Hamiltonian stories once the discrete
bridge is working.

## Quarter-turn `J` seam

The local archive check sharpened one especially important bridge object:
the quarter-turn `J`.

Operationally, `J` is useful as:

- local complex structure in an otherwise real representation
- phase-rotation generator
- bridge between lattice-local 2-planes and qubit-like measurement axes

In implementation terms, `J` should be treated as a reusable generator that can
live inside both:

- the invertible evolution seam
- the observable/measurement framing of local planes

This is currently the cleanest bridge between the lattice-facing `dashifine`
experiments and the Agda quantum split.

## Current ownership split

### `dashiQ`

Should own:

- the bridge note
- the abstract interface
- the first toy simulator
- the language distinguishing latent state from measured datum

### `dashifine`

Should continue to own:

- concrete classical quantum-faithful experiments
- CHSH / qutrit / SSH / triality prototypes
- local `J`-plane and lattice tests

### `FRACDASH`

Supplies a different kind of reuse:

- compiler / bridge-correctness language
- explicit source -> executable IR -> target split
- encode / decode / abstraction obligations
- quotient / compression claim discipline
- executable witness and status reporting

That is useful for `dashiQ`, but it should not be confused with the quantum
state interface itself.

`FRACDASH` is currently strongest as a model for:

- how to state what the source semantics are
- how to state what the target executable semantics are
- how to separate exact claims from weaker observational claims
- how to record what is only local/executable versus what is inherited from
  `dashi_agda`

## What `FRACDASH` changes

`FRACDASH` does not currently supply the quantum carrier or measurement layer.
It does sharpen the bridge discipline for `dashiQ`.

Operationally, the `FRACDASH` contribution is:

```text
source semantics
-> bridge / signed executable IR
-> target executable realization
-> decoder / observable report
```

That sits across the Agda quantum split rather than replacing it.

The useful synthesis is:

```text
latent state
-> invertible evolution
-> projection / measurement
-> observable
-> executable bridge / decoder obligations
```

So `dashiQ` should borrow from `FRACDASH` the following implementation
requirements:

- name the source semantics explicitly
- name the internal executable carrier explicitly
- name the readout / decoder explicitly
- distinguish exact state evolution claims from observable-only claims
- state which coarse projections are semantic quotients rather than mere
  numerics
- add witness/status reporting once there is a real simulator path

### What not to import directly

`FRACDASH` is FRACTRAN-facing and signed-register-facing. `dashiQ` should not
adopt:

- FRACTRAN-specific target semantics
- prime-exponent carrier assumptions
- integer-register execution as the quantum carrier itself

Those are examples of executable bridge discipline, not the quantum formalism.

## Recommended first implementation target

The first actual `dashiQ` implementation should be a toy system with:

- latent state in a small qubit/qutrit-or-real-`J` carrier
- an explicitly invertible `step`
- an idempotent coarse `project`
- a separate `measure`
- at least one observable:
  - CHSH `S`
  - spectral gap
  - coarse motif distribution
  - MDL/code-length proxy
- an explicit decode / report layer for whatever classical output the simulator
  exposes
- a minimal witness/status record describing:
  - carrier family
  - whether `step` is exact or only approximate
  - whether `project` is idempotent by construction or empirical
  - whether observables are exact, bounded, or heuristic

The simplest path is probably:

1. start from local `J`-plane state + reversible rotation
2. add coarse projection to a motif or plane summary
3. expose one Bell/CHSH observable through the same interface
4. add a tiny `FRACDASH`-style decoder/witness surface so the bridge makes
   explicit claims rather than just producing plots

That gets the bridge into a form where the existing `dashifine/newtest`
material can plug in without pretending we already have a hardware compiler.

## Current runtime status

This repo now has two concrete Python runtime layers:

- `computer_v1.py`
  - seam-oriented prototype
  - direct inspection of the first qubit / qutrit / triality loops
  - now emits a v2-compatible witness shape at the field level
- `computer_v2.py`
  - typed carrier-dispatch layer
  - `CarrierType = QUBIT | QUTRIT | TRIALITY`
  - measurement / promotion / selection / witness / gap are dispatched by carrier
  - this is now the default place for further carrier/runtime growth

The qutrit side is now split into two runtime families:

- `qutrit_planes`
  - two-qutrit embedded state in 9D
  - projection selection across basis9 permutations (entropy-gap + coherence)
  - basis-distribution measurement and entropy-gap observable
- `qutrit_motif27`
  - 27-state latent carrier
  - `27 -> 9` motif coarse-graining through
    `dashifine/newtest/map_27_to_H3x3.py`
  - projection selection across motif-rolls (entropy-gap + coherence)
  - motif-entropy-gap observable with selection metadata
  - motif weights now enter an additive comparison program through a shared
    `qg_motif_models` layer
  - default baseline remains `qg_dynamics`
  - candidate models are:
    - `qg_mdl`
    - `qg_dynamics`
    - `qg_large_tail`
    - `qg_ensemble`
    - `qg_projection_covariant`
    - `qg_triality_coupled`
    - `qg_ccr_experimental`
  - witness/reporting now keeps baseline plus comparison models visible side
    by side; older structured and uniform presets remain explicit baselines
  - current policy is baseline-first: a comparison model only displaces
    `qg_dynamics` if it improves both projection score and entropy-gap and is
    not marked experimental

The triality side is now carrier-native too:

- `triality_frames`
  - uses extracted leg-plane data from the near-zero wall mode
  - evaluates all leg pairs
  - selects by theory-weighted multi-criterion score (strength/stability/
    symmetry; weights configurable via prep metadata, optional
    `triality_selection_model=mdl` preset derived from norm dispersion),
    with explicit signal/stability/symmetry code costs and `exp(-mdl_cost)`
    selection recorded in witness
  - promotes on score gate plus pair-correlation stability

So the main remaining issue is no longer architectural typing. It is the
quality of the carrier-native semantics:

- `qutrit_motif27` now has a first Agda-inspired preparation generator, but it
  is still a code-length proxy rather than a fuller QG dynamics source

## Non-goals for this stage

This document does not claim:

- quantum hardware execution
- quantum advantage
- a finished Born-rule derivation
- full CCR / Stone / field-theory closure
- that p-adic formalism already implies a hardware path

Those are later questions. The bridge-first task is only to stabilize the
internal interface.
